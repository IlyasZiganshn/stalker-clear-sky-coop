# Архитектура

Документ описывает целевую конструкцию кооперативного мода для S.T.A.L.K.E.R.: Clear Sky.
Это проект решения, а не отчёт о готовом коде: часть пунктов помечена как требующая проверки
на живом движке (см. [ROADMAP.md](ROADMAP.md), спайки M1).

## 1. Границы задачи

В scope:

- Прохождение сюжетной кампании Clear Sky вдвоём-вчетвером, включая faction war и переходы между локациями.
- Совместные бои с NPC и мутантами, общий инвентарь мира (предметы на земле, тайники, торговцы).
- Единое состояние сюжета: квесты, диалоги, катсцены, захват точек, репутация у группировок.

Вне scope v1:

- PvP и балансировка под соревновательную игру.
- Серверы на 8+ игроков и «живой мир» как в Anomaly/CoC.
- Совместимость со сторонними модами и сборками.
- Античит уровня онлайн-шутера. Достаточно серверной валидации от рассинхрона и наивных читов.

## 2. База: почему OpenXRay

| Вариант | Вердикт |
|---|---|
| Оригинальный X-Ray 1.5.10 (закрытый) | Нет: нет исходников, x64, невозможен нормальный netcode |
| xrMPE | Нет как база: закрытый движок, только CoP 1.6.02 |
| OpenXRay (`dev`) | Да: открытый, x64, CS 1.5.10 поддерживается, C++20, Windows + Linux |

Важный бонус OpenXRay: в коде сохранился исходный (мёртвый в ретейле) мультиплеерный слой
X-Ray — `NET_Packet`, `CClient`/`CServer`, хуки приёма пакетов в `CLevel`. Он нерабочий
и не покрывает наши задачи, но даёт готовый формат сериализации и точки подключения,
которые не надо изобретать. Использовать его как основу wire-формата — решение по умолчанию,
окончательно подтверждается на спайке M1.

Версия движка фиксируется тегом/коммитом форка. Апстрим двигается, поэтому:

- `engine/` содержит только наши патчи и скрипт их применения к зафиксированному коммиту OpenXRay;
- обновление форка — отдельная задача, не «подтянуть dev и посмотреть».

## 3. Модель авторитета

Один авторитетный экземпляр игры — **сервер**. Он владеет симуляцией: AI, физика, скрипты,
спавн, состояние мира. Клиенты — представление плюс предсказание собственного персонажа.

```
               ┌──────────────────────────┐
               │  Server (listen/dedicated)│
               │  full game sim, no render │
               └───────┬──────────┬───────┘
             snapshots │          │ snapshots
                 ┌─────▼───┐  ┌───▼─────┐
                 │ Client A│  │ Client B│
                 │ predict │  │ predict │
                 │ +interp │  │ +interp │
                 └─────────┘  └─────────┘
```

Решения:

1. **Listen server по умолчанию.** Хост играет и одновременно симулирует. Для тестов и
   «сервера 24/7» — dedicated-режим с отключённым рендером, звуком и вводом.
2. **Headless-режим — риск №1.** X-Ray исторически завязан на `CRenderDevice` и синглтоны
   (`g_pGameLevel`, `Level()`, `Device`). Надо проверить, достаточно ли отключить рендер
   и ввод, или потребуется развязывать кадровый цикл от рендера. Если развязывать —
   это отдельный крупный патч движка.
3. **Клиент не присылает результат своих действий.** Клиент отправляет намерение
   (input + команды), сервер считает попадания, урон, подбор предметов, смерть.
   Исключение — полностью локальные косметические эффекты (гильзы, декали, звук шагов).

## 4. Слои

| Слой | Где живёт | Содержимое |
|---|---|---|
| L0 Транспорт | `coopnet` | UDP, каналы (reliable ordered / reliable unordered / unreliable sequenced), фрагментация, MTU, keepalive, RTT |
| L1 Кодек | `coopnet` | битовый поток, varint/zigzag, квантование позиций и углов, снапшоты и дельты |
| L2 Репликация | движок + `coopnet` | сетевые id ↔ `object_id`, таблицы сущностей, interest management, спавн/деспавн |
| L3 Игровой слой | движок | игроки, оружие, урон, инвентарь, физика, транспорт |
| L4 Скриптовый слой | `gamedata/scripts` | task_manager, диалоги, переходы уровней, faction war, катсцены |
| Инструменты | `tools` | инспектор снапшотов, дамп трафика, реплей, логи рассинхрона |

Разделение важно: L0–L1 не знают про X-Ray и тестируются юнит-тестами без игры.
L2+ уже требует движка и запуска игры.

## 5. Что реплицируется и как

| Домен | Владелец | Частота | Точность |
|---|---|---|---|
| Позиция/поворот игрока | сервер (валидирует клиентское предсказание) | 20 Гц снапшот, 60 Гц input | позиция ~6 мм, углы 16 бит |
| Состояние персонажа (стойка, оружие, анимация) | сервер | по изменению | enum + флаги |
| Выстрелы | клиент → сервер как намерение, сервер → всем как событие | событие | траектория/хит — сервер |
| Урон и здоровье | сервер | по изменению | u16 |
| NPC/мутанты | сервер | 10–20 Гц, по расстоянию | позиция + состояние AI |
| Предметы в мире | сервер | по изменению | id + трансформ |
| Инвентарь | сервер | по изменению | список слотов/стаков |
| Скриптовые события | сервер | событие | RPC по имени с аргументами |

Interest management: клиент получает сущности в радиусе и в «зоне сюжета»; дальние NPC
обновляются реже (LOD репликации). Это критично для полосы: полный снапшот локации
с десятками NPC и физикой не влезет в бюджет.

## 6. Время и тик

- Симуляция сервера — переменный `dt` кадра, как в оригинале, но сетевой тик фиксирован:
  60 Гц приём/отправка ввода, 20 Гц снапшоты.
- Снапшоты нумеруются `tick` (u32) и строятся относительно подтверждённой базы (дельта).
- Клиент буферизует снапшоты на ~100 мс и интерполирует чужие сущности.
- Свой персонаж: предсказание, при расхождении — реконсиляция из последнего ack-снапшота.
- Физика X-Ray не детерминирована между машинами. Значит, физические объекты
  (ящики, трупы, тряпки) авторитетны на сервере, клиент их только интерполирует.
  Предсказывать можно исключительно кинематику персонажа по упрощённой модели.

## 7. Идентификаторы

- `object_id` в X-Ray — u16, уникален в пределах уровня и переиспользуется.
- Вводится `net_id`: u32, монотонный на сессию, выдаётся сервером при спавне сущности.
- Таблица `net_id → object_id` живёт на сервере и на клиентах; заполняется сообщением спавна.
- При смене уровня таблица очищается, `net_id` продолжают счёт (сквозная нумерация сессии).

## 8. Скриптовый слой и сюжет

Сюжет Clear Sky — это скрипты (`task_manager`, `dialogs`, `xr_conditions`/`xr_effects`,
`smart_terrain`, `sim_squad_scripted`), а не движковые данные. Поэтому кооп нельзя
сделать «только на движке».

Модель:

1. **Story owner** — сервер. Он единственный выполняет сюжетные скрипты в полном объёме
   и владеет состоянием задач.
2. **Зеркало на клиентах.** Клиент не выполняет ветки логики, которые меняют мир;
   он получает состояние задач, активных диалогов и флагов и рисует UI.
3. **Диалоги.** Открывает один игрок; остальные видят, что диалог идёт, и не могут
   вклиниться. Выбор реплики — за инициатором.
4. **Катсцены и рестрикторы.** Вход в катсцену блокирует ввод всем; камера — локальная,
   чтобы каждый видел сцену от себя.
5. **Faction war.** Симуляция группировок целиком на сервере; клиент получает состояние
   точек и отношений. Один «сюжетный» игрок не должен становиться узким местом —
   действия любого игрока идут в общую симуляцию.

Практический приём: не переписывать скрипты CS, а обернуть их — перехватывать
`task_manager`, `dialogs` и `sim_squad_scripted` тонким слоем `gamedata/scripts/coop/*`,
который отправляет и применяет RPC. Это уменьшает объём правок и упрощает откат.

## 9. Переходы между уровнями

Самый недооценённый кусок. В CS локации грузятся при переходе, вместе с ними меняется
весь мир и `object_id`.

Двухфазный протокол:

1. Сервер фиксирует состав группы и запускает переход.
2. `S_LEVEL_PRELOAD` — клиенты грузят целевой уровень, показывают экран загрузки
   с прогрессом. Все шлют `C_LEVEL_READY`.
3. Когда все готовы (или истёк таймаут), сервер применяет переход: спавн группы
   на точке выхода, рассылка `S_LEVEL_GO` с новой таблицей сущностей.
4. Отвалившиеся в процессе — в лобби с возможностью реконнекта в тот же уровень.

Требуется остановка симуляции на время загрузки у всех: иначе игроки «живут» в разных
уровнях. Это осознанное ограничение: загрузка локации — общая пауза 5–15 секунд.

## 10. Сохранения и восстановление

- Сохранение делает сервер; клиентские сейвы не используются.
- Чекпойнт = состояние `alife()` + состояние уровня + позиции игроков + состояние задач.
- Реконнект клиента: полный снапшот мира (не дельта), возврат в ту же точку.
- Смерть игрока: `death`/`revive` — либо respawn у медика/базы, либо подъём напарником
  (решается на этапе M2, влияет на баланс).

## 11. Валидация и устойчивость

- Сервер проверяет скорость и телепорты игрока, попадания (по своим расчётам),
  дистанцию взаимодействия с предметами.
- Ограничение частоты и размера пакетов; неизвестные сообщения — лог и дроп, не краш.
- Версия протокола и хеш сборки проверяются на handshake: несовпадение — понятная ошибка,
  а не «невидимые игроки».

## 12. Производительность: бюджет

Ориентир для 4 игроков и ~60 активных NPC:

- снапшот 20 Гц, дельта ≤ 1.5 КБ в среднем → ~240 Кбит/с на клиента;
- input 60 Гц, ~40 байт → ~20 Кбит/с;
- события/скрипты — по требованию, вне бюджета.

Если не влезаем — режем частоту для дальних сущностей, а не точность ближних.
Замеры — обязательная часть M1: без цифр оптимизировать нечего.

## 13. Известные риски

| Риск | Почему опасен | Что делаем |
|---|---|---|
| Headless-сервер | X-Ray завязан на рендер и `Device` | спайк M1, при провале — listen-only |
| Несинхронная физика | физика не детерминирована | только серверная симуляция физики |
| Скрипты CS меняют мир напрямую | кооп ломает инварианты квестов | обёртки вместо переписывания, RPC-слой |
| Переходы уровней | общая пауза, потеря состояния | двухфазный протокол, тесты на каждой локации |
| Стоимость AI на сервере | 4 клиента + AI = CPU | LOD репликации, отключение дальнего AI |
| Объём работы | годы, а не месяцы | жёсткие этапы с критериями, вертикальный срез первым |
