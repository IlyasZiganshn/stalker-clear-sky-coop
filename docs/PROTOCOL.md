# Протокол

Версия: 2 (черновик, до первого спайка). Всё ниже — контракт, который меняется только
с повышением версии.

## Транспорт

- UDP, один сокет. MTU полезной нагрузки — 1200 байт, крупные сообщения фрагментируются.
- Четыре канала:

| Канал | Гарантии | Что ходит |
|---|---|---|
| 0 control | reliable ordered | handshake, загрузка уровня, скриптовые RPC |
| 1 events | reliable ordered | выстрелы, попадания, подбор, смерть |
| 2 snapshot | unreliable sequenced | состояние мира (старые снапшоты отбрасываются) |
| 3 input | unreliable | ввод клиента и ack |

- Keepalive 1 Гц, разрыв — 5 секунд без пакетов. Любой корректный датаграмм
  считается признаком жизни, включая пустой `ACK_ONLY`.

Заголовок каждого датаграмма — ровно 12 байт:

```
[u16 protocol_version][u8 channel][u8 flags][u16 seq][u16 ack][u32 ack_bits][payload]
```

- `seq` — номер датаграмма в пределах канала (u16, с переполнением).
- `ack` / `ack_bits` — подтверждения: `ack` — последний полученный номер, бит i
  означает «получен номер ack-1-i».
- `flags` — `RELIABLE`, `FRAGMENT`, `ACK_ONLY`, `KEEPALIVE`.
- `KEEPALIVE` — датаграмм без полезной нагрузки (12 байт заголовка), уходит по
  control-каналу, если за интервал не отправлено ничего другого. Не нумерует
  сообщения, не подтверждается и не доставляется; поля `ack`/`ack_bits` в нём
  действительны, так что keepalive попутно снимает ретрансмиты.

Реализация: `coopnet/wire.h`, `coopnet/session.h`.

## Надёжность

- Надёжные каналы (control, events): каждый датаграмм нумеруется, получатель
  доставляет строго по порядку, отправитель ретранслирует неподтверждённое.
- RTO стартует со 100 мс и удваивается до 500 мс. Окно — 32 сообщения и не более
  32 номеров разброса: иначе потерянный пакет выпал бы из 32-битной маски
  подтверждений и ретранслировался бы вечно.
- Пакет без полезной нагрузки с флагом `ACK_ONLY` подтверждает приём, когда
  отправителю нечего сказать. На `ACK_ONLY` никогда не отвечают `ACK_ONLY` —
  иначе два конца будут перекидываться пустыми пакетами.
- RTT измеряется по времени между первой отправкой сообщения и подтверждением,
  снимающим его из очереди; берётся только самый новый подтверждённый номер,
  чтобы ретрансмит не завышал, а старое подтверждение не занижало оценку.
  Сглаживание — `(7*prev + sample) / 8`, стартовое значение — первый замер.
  Время отправки запоминается один раз, поэтому повторные отправки в замер не
  попадают. Оценка доступна наружу как `Session::rttMs()`.

## Фрагментация

- Бюджет полезной нагрузки датаграмма = `mtu - 12`. Если сообщение больше,
  оно режется на куски; перед каждым куском 8-байтный заголовок:
  `[u32 message_id][u16 index][u16 count]`.
- Фрагмент — обычное надёжное сообщение с флагом `FRAGMENT`: он занимает номер
  в последовательности, ретранслируется вместе с флагом и доставляется
  получателю в общем упорядоченном потоке. Сборка идёт только из этого потока,
  поэтому порядок кусков гарантирован порядком канала, а не порядком прихода
  датаграмм.
- Ненадёжные каналы не фрагментируются: собрать сообщение из пакетов без
  гарантии доставки нельзя. Снапшот и ввод обязаны укладываться в один датаграмм,
  иначе `send()` возвращает `false`.
- Сборка сообщения ограничена таймаутом (5 с), после чего недособранное
  выбрасывается и отправитель начинает заново.
- Фрагменты одного сообщения ставятся в очередь подряд, поэтому сообщение
  доставляется сразу после последнего куска, в общем порядке канала.

## Ещё не реализовано

Реконнект, обработка таймаута соединения на уровне пиров (таймаут `Session` уже
есть), диспетчеризация игровых сообщений — M1–M2. Формат сообщений выше —
контракт, который эта реализация должна соблюдать.

## Handshake

Сообщения идут по каналу control. Первый байт — опкод:

| Опкод | Сообщение |
|---|---|
| 1 | `C_HELLO` |
| 2 | `S_HELLO_ACK` |
| 3 | `C_JOIN` |
| 4 | `S_JOIN_OK` |
| 5 | `S_JOIN_DENY` |

```
C_HELLO      { u8 op, u16 proto, u32 build_hash, string name, u32 token }
S_HELLO_ACK  { u8 op, u32 client_id, u32 session, u16 snap_hz, u16 tick_hz }
C_JOIN       { u8 op, u8 slot }
S_JOIN_OK    { u8 op, u32 net_id, ServerRules rules }
S_JOIN_DENY  { u8 op, u8 reason }

ServerRules  { u8 difficulty, u8 max_players, bool friendly_fire,
               align, u8 time_speed_percent }
string       { u16 length, align, u8 bytes[length] }   // UTF-8, length <= 32
```

- Все значения многобайтные — little-endian; после строк и `bool` поток
  выравнивается на байт.
- Декодирование строгое: неверный опкод, обрезанные или лишние байты,
  неизвестная причина отказа и имя длиннее 32 байт — ошибка формата.
- `build_hash` — хеш сборки движка и набора скриптов. Несовпадение = отказ с
  человеческим текстом. `token` — для реконнекта в течение сессии (0 при первом
  подключении).
- Причины отказа: 1 — версия протокола, 2 — билд, 3 — сервер полон, 4 — имя,
  5 — занято, 6 — бан.
- `C_JOIN.slot` — предпочитаемый слот: `0..max_players-1` или `0xFF` («любой
  свободный»). Сервер вправе назначить другой; клиент узнаёт свою идентичность по
  `net_id` из `S_JOIN_OK`, слот ему не нужен.

Реализация: `coopnet/handshake.h`, `coopnet/src/handshake.cpp`.

## Снапшоты

Снапшот строится дельтой от последнего подтверждённого клиентом:

```
S_SNAPSHOT {
  u32 tick
  u32 base_tick          // 0 = полный снапшот
  u32 last_processed_input  // последний тик C_INPUT, применённый сервером
  u16 entity_count
  entity[] {
     u32 net_id
     u8  class            // player / stalker / mutant / item / physics / ...
     u16 present_mask     // какие поля есть в записи
     ...поля по маске
  }
  u32 removed_count
  u32 removed_net_id[]
}
```

Поля по маске (порядок фиксирован):

| Бит | Поле | Кодирование |
|---|---|---|
| 0 | position | 3×15 бит в AABB локации |
| 1 | velocity | 3×12 бит, ±32 м/с |
| 2 | yaw/pitch | 2×16 бит |
| 3 | state | u8 enum (idle/walk/run/crouch/...), u8 флаги |
| 4 | health | u16 |
| 5 | weapon | u8 слот, u8 состояние |
| 6 | anim_phase | u8 |
| 7 | ai_state | u8 |
| 8 | owner_net_id | u32 (для предметов в руках/контейнерах) |
| 9 | extra | переменная длина, класс-специфично |

Сервер строит дельту от последнего снапшота, который клиент **подтвердил** в
`C_INPUT.ack_snapshot`, а не от просто отправленного. Поэтому потеря снапшота не
рвёт цепочку: следующий придёт от той же подтверждённой базы и применится.

Клиент хранит последние 16 применённых состояний (`SnapshotStore::kHistory`) и
применяет дельту к любому сохранённому состоянию с нужным `base_tick`:
- база есть в истории — дельта применяется, результирующее состояние запоминается;
- `tick` снапшота не новее текущего — снапшот устарел и игнорируется;
- базы нет (отставание больше 16 тиков) — дельта отклоняется, клиент ждёт
  полный снапшот. Запрос `C_RESYNC` (счётчик попыток с backoff) — M2.

Полный снапшот уходит, если клиент ещё ничего не подтвердил или его `ack_snapshot`
отстал больше чем на 20 тиков (1 с при 20 Гц). На клиенте полный снапшот с тиком
старше текущего отбрасывается.

Реализация: `coopnet/delta.h`, `coopnet/client_replicator` (`replicator.h`),
`coopnet/snapshot_store.h`.

## Клиентская интерполяция

- Снапшоты складываются в буфер по локальному времени прихода; кадр рисуется в
  момент `now - delay`, где `delay` — не меньше двух интервалов снапшотов.
- Позиция, скорость и углы линейно смешиваются между соседними снапшотами.
  Рыскание интерполируется по короткой дуге (350° → 10° через 0), тангаж — без
  заворачивания. Дискретные поля (состояние, оружие, здоровье) берутся из старого
  снапшота пары и меняются, когда время отрисовки проходит новый.
- За последним снапшотом экстраполяции нет: состояние держится до следующего
  пакета. Список сущностей определяется новым снапшотом, поэтому удаление
  срабатывает при переходе через его время.
- Буфер ограничен 32 снапшотами; снапшоты старше последнего по времени прихода
  игнорируются.

Реализация: `coopnet/interp.h`.

## Ввод

```
C_INPUT {
  u32 tick
  u32 ack_snapshot          // последний применённый снапшот
  i16 move_x, move_y        // -32768..32767 → -1..1
  u16 view_yaw, view_pitch
  u16 buttons               // битовая маска: fire, aim, jump, crouch, sprint, use, reload, ...
  u8  weapon_slot
}
```

Отправляется 60 Гц. Каждый тик остаётся в отправке, пока его не вытеснят новые:
клиент шлёт последние 8 тиков (~130 мс), поэтому потерянный датаграмм
перекрывается повтором того же тика. Сервер применяет ввод строго по порядку:
ввод, пришедший впереди пропуска, буферизуется и ждёт недостающий тик; если
дырка не закрылась за 32 тика, она считается потерянной и актор двигается
дальше, а не замирает. Сервер отвечает в снапшоте полем `last_processed_input`
для реконсиляции.

## Предсказание и сверка

- Клиент применяет ввод своего тика локально сразу, той же функцией шага
  движения, что и сервер: иначе предсказание и авторитет разойдутся.
- Каждый предсказанный тик записывается в историю; сервер подтверждает
  обработанные тики (в снапшоте — `last_processed_input`).
- При авторитетной коррекции клиент отбрасывает подтверждённые тики, ставит
  состояние сервера и повторно применяет оставшиеся входы по порядку. Повторный
  или более старый `last_processed_input` ничего не подтверждает, но оставшиеся
  входы всё равно повторяются; историю клиент очищает только когда ack не старше
  последнего предсказанного тика.
- История ограничена 256 тиками (~4 с при 60 Гц); при переполнении самый старый
  вход выбрасывается — к этому моменту связь уже мертва.

Реализация: `coopnet/prediction.h` (история), `coopnet/client_predictor.h`
(предсказание и реконсиляция), `coopnet/movement.h` (общий шаг движения).

## Прикладные сообщения

Мелкие редкие сообщения (чат, уведомления, позже — скриптовый RPC) ходят по каналу
control с надёжной доставкой. Первый байт — тип; значения 1..5 заняты рукопожатием,
поэтому прикладные типы начинаются с `0x10` (иначе peer примет сообщение за часть
handshake и не отдаст приложению).

```
C_CHAT {
  u8  type = 0x10
  u32 sender        // net_id автора; клиент отправляет 0
  u16 length        // 1..200 байт
  u8  text[length]  // UTF-8 как есть
}
```

- Сервер подставляет `sender` по `net_id` отправителя и рассылает сообщение всем
  присоединённым, кроме автора. Хост рассылает своё сообщение всем.
- Декодирование строгое: неизвестный тип, пустой текст, несовпадающая длина и
  лишние байты — сообщение отбрасывается.
- Тот же формат используется мостом движка: `coop_say <text>` и последняя
  полученная строка в `coop_status`.

Реализация: `coopnet/app_message.h`, демо `tools/coopnet_chat`,
`engine/patches/files/xrNetServer/coop/coop_bridge.cpp`.

## Состояние игрока

Трансформ локального персонажа ходит отдельным сообщением по тому же control-каналу.
Полный снапшот мира для этого ещё не нужен: пока синхронизируется только позиция и
поворот игроков, а частота низкая.

```
C_PLAYER {
  u8  type = 0x11
  u32 net_id
  f32 x, y, z
  f32 yaw
}
```

- Размер фиксированный — 21 байт. `net_id` не может быть 0, NaN и бесконечности
  отбрасываются и на кодировании, и на декодировании.
- Клиент отправляет своё состояние; сервер подставляет `net_id` отправителя и
  пересылает всем, кроме него. У хоста нет `net_id`, поэтому его трансформ идёт
  под зарезервированным `1` (клиентские id начинаются с 1000).
- Мост ограничивает частоту сам (20 Гц), поэтому движок может вызывать публикацию
  каждый кадр. Полученные чужие трансформы живут 2 с: молчание дольше — игрок
  считается пропавшим.

Сервер отслеживает переходы «вошёл/вышел» (`NetServer::takeEvents`) и при уходе
игрока рассылает остальным:

```
C_PLAYER_GONE {
  u8  type = 0x12
  u32 net_id
}
```

Клиент по нему сразу забывает трансформ, не дожидаясь двухсекундного таймаута.
Если сессия потеряла сервер, приложение замечает это по `timedOut()` клиента.

## Мир и игровые часы

Сервер — источник истины по уровню и игровому времени. После входа он сразу
отправляет новому клиенту `C_WORLD`, дальше повторяет раз в секунду:

```
C_WORLD {
  u8  type = 0x13
  u64 game_time_ms   // игровые часы хоста
  u8  name_length    // 1..64
  u8  level_name[name_length]
}
```

- Клиент отправляет своё `C_WORLD` один раз после входа; сервер его не
  пересылает, но по нему видно, что клиент уже загрузил уровень.
- Клиент сравнивает имя уровня с локальным. Расхождение — статус
  `coop: level mismatch (...)` и разрыв сессии: играть на разных локациях нельзя.
- Оценка часов сервера: `BridgeServerGameTime()` = последний `game_time_ms` плюс
  локальные миллисекунды с момента получения. RTT пока не вычитается, поэтому
  точность — порядка задержки; для перевода мира на общие часы этого хватит.

Реализация: `coopnet/player_state.h`, демо `tools/coopnet_world`, мост
`BridgePublishLocalPlayer`/`BridgeRemotePlayers`.

## Спавн игроков

Одного трансформа мало: у каждого участника должен появиться чужой персонаж.
После входа обе стороны обмениваются сериализованным спавном своего актора.
Блоб — это байты `CSE_Abstract` (начинаются с `M_SPAWN`), `coopnet` их не
разбирает и не проверяет: формат принадлежит движку.

```
C_SPAWN {
  u8  type = 0x14
  u32 net_id
  u16 length        // 1..4096
  u8  blob[length]
}

C_SPAWN_GONE {
  u8  type = 0x15
  u32 net_id
}
```

- Клиент после входа отправляет свой спавн; сервер подставляет `net_id`
  отправителя, запоминает блоб и рассылает остальным. Поздний гость получает
  все известные спавны сразу после рукопожатия.
- Сервер отправляет свой спавн под `net_id = 1` каждому новому пиру; повторная
  доставка безопасна — получатель игнорирует уже известный `net_id`.
- `net_id` — единственный общий идентификатор. Игровые ID (`object_id`) локальны
  для процесса: каждая сторона выделяет чужому игроку свой свободный ID
  (диапазон `0xF000+`) и перезаписывает поле `ID` в блобе перед спавном.
- Клиент не принимает спавн со своим `net_id`; пустой, слишком большой или
  обрезанный блоб, а также неверный заголовок `M_SPAWN` отбрасываются.
- При выходе игрока сервер шлёт `C_SPAWN_GONE` (вместе с `C_PLAYER_GONE`):
  получатель удаляет куклу, не дожидаясь таймаута трансформа.

Реализация: `coopnet/spawn.h`, демо `tools/coopnet_spawn`, мост
`BridgeSetLocalSpawn`/`BridgeTakeSpawns`/`BridgeTakeDespawns`, движковая часть —
`engine/patches/files/xrGame/coop/coop_player.cpp`.

## События

```
S_EVENT {
  u8  type
  ...зависит от типа: SHOT, HIT, PICKUP, DEATH, SCRIPT
}
```

- `SHOT` — кто, из чего, направление; трассер и звук у всех.
- `HIT` — только сервер: цель, часть тела, урон, тип боеприпаса.
- `SCRIPT` — `u16 rpc_id` + аргументы; таблица RPC генерируется из Lua-описаний
  на этапе M4, вручную не поддерживается.

## Скриптовый RPC (L4)

```
S_SCRIPT {
  u16 rpc_id
  u8  argc
  value[]   // tagged: u8 type + payload (nil/bool/int/float/string/hash)
}
```

Сервер вызывает RPC на клиентах, клиент — только запросы к серверу
(`C_SCRIPT_REQ`), результат возвращается событием. Клиент никогда не вызывает
мир-меняющие RPC напрямую.

## Квантование

- Позиция: 15 бит на компоненту в AABB уровня. Для локации 500×500 м это ~1.5 см;
  для 200×200 м — 6 мм. Точность настраивается на уровень.
- Углы: рыскание — 16 бит на полный оборот (0.0055°), тангаж — 16 бит на диапазон
  ±90°. Тангаж знаковый и не заворачивается: иначе взгляд вниз интерполируется
  через «вверх».
- Скорость: 12 бит, ±32 м/с, шаг 1.5 см/с.
- Здоровье: u16, 1 единица.

Все float в протоколе — либо квантованные целые, либо IEEE-754 как есть
(для нечастых полей). Никакой платформенной зависимости от `float`-порядка байт:
запись/чтение через `memcpy` в u32.

## Версионирование

- `protocol_version` растёт при несовместимом изменении. Совместимые расширения —
  новые биты маски и новые типы событий; старый клиент их игнорирует.
- Схема снапшота и таблица RPC версионируются вместе с протоколом, не отдельно.

## Ошибки и лимиты
