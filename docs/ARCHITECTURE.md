# Архитектура кооперативного режима

Документ описывает, как сетевой слой `coopnet` и движок OpenXRay соединяются в
играбельный кооп, и каким должен стать целевой мод. Реализованы транспорт,
прикладные сообщения, трансформы игроков, сведения о мире, спавн чужих игроков
и ввод с симуляцией кукол на хосте; дальше — сущности мира и владение акторами.
Часть пунктов ещё требует проверки на живом движке (спайки M1, см.
[ROADMAP.md](ROADMAP.md)).

## 1. Границы задачи

В scope:

- Прохождение сюжетной кампании Clear Sky вдвоём-вчетвером, включая faction war
  и переходы между локациями.
- Совместные бои с NPC и мутантами, общий инвентарь мира (предметы на земле,
  тайники, торговцы).
- Единое состояние сюжета: квесты, диалоги, катсцены, захват точек, репутация
  у группировок.

Вне scope v1:

- PvP и балансировка под соревновательную игру.
- Серверы на 8+ игроков и «живой мир» как в Anomaly/CoC.
- Совместимость со сторонними модами и сборками.
- Античит уровня онлайн-шутера. Достаточно серверной валидации от рассинхрона
  и наивных читов.

## 2. База: почему OpenXRay

| Вариант | Вердикт |
|---|---|
| Оригинальный X-Ray 1.5.10 (закрытый) | Нет: нет исходников, x64, невозможен нормальный netcode |
| xrMPE | Нет как база: закрытый движок, только CoP 1.6.02 |
| OpenXRay (`dev`) | Да: открытый, x64, CS 1.5.10 поддерживается, C++20, Windows + Linux |

Важный бонус OpenXRay: в коде сохранился исходный (мёртвый в ретейле)
мультиплеерный слой X-Ray — `NET_Packet`, `CClient`/`CServer`, хуки приёма
пакетов в `CLevel`. Он нерабочий и не покрывает наши задачи, но даёт готовый
формат сериализации и точки подключения, которые не надо изобретать.

Версия движка фиксируется коммитом форка. Апстрим двигается, поэтому:

- `engine/` содержит только наши патчи и скрипт их применения к зафиксированному
  коммиту OpenXRay;
- обновление форка — отдельная задача, не «подтянуть dev и посмотреть».

## 3. Роли и авторитет

Один авторитетный экземпляр игры — **хост**. Он владеет симуляцией: AI, физика,
скрипты, спавн, состояние мира. Клиенты — представление плюс предсказание
собственного персонажа.

- **Хост** — авторитарный сервер, у него запущен обычный одиночный мир Clear Sky:
  ALife, скрипты, погода, время, физика. Все решения о мире принимает он.
- **Клиент** — тонкий игрок: отправляет ввод, получает снапшоты, предсказывает
  только собственное движение. ALife и скрипты на клиенте не выполняются.
- Кооп на 2–4 игрока; выделенного сервера в первой версии нет (listen-хост).

```
               ┌──────────────────────────┐
               │  Server (listen/dedicated)│
               │  full game sim, no render │
               └───────┬──────────┬───────┘
             snapshots │          │ snapshots
                 ┌─────▼───┐  ┌───▼─────┐
                 │ Client A│  │ Client B│
                 │ predict │  │ predict │
                 │ +interp │  │ +interp │
                 └─────────┘  └─────────┘
```

Решения:

1. **Listen server по умолчанию.** Хост играет и одновременно симулирует. Для
   тестов и «сервера 24/7» — dedicated-режим с отключённым рендером, звуком
   и вводом.
2. **Headless-режим — риск №1.** X-Ray исторически завязан на `CRenderDevice`
   и синглтоны (`g_pGameLevel`, `Level()`, `Device`). Надо проверить, достаточно
   ли отключить рендер и ввод, или потребуется развязывать кадровый цикл
   от рендера. Если развязывать — это отдельный крупный патч движка.
3. **Клиент не присылает результат своих действий.** Клиент отправляет намерение
   (input + команды), сервер считает попадания, урон, подбор предметов, смерть.
   Исключение — полностью локальные косметические эффекты (гильзы, декали,
   звук шагов).

## 4. Слои

| Слой | Где живёт | Содержимое |
|---|---|---|
| L0 Транспорт | `coopnet` | UDP, каналы (reliable ordered / reliable unordered / unreliable sequenced), фрагментация, MTU, keepalive, RTT |
| L1 Кодек | `coopnet` | битовый поток, varint/zigzag, квантование позиций и углов, снапшоты и дельты |
| L2 Репликация | движок + `coopnet` | сетевые id ↔ `object_id`, таблицы сущностей, interest management, спавн/деспавн |
| L3 Игровой слой | движок | игроки, оружие, урон, инвентарь, физика, транспорт |
| L4 Скриптовый слой | `gamedata/scripts` | task_manager, диалоги, переходы уровней, faction war, катсцены |
| Инструменты | `tools` | инспектор снапшотов, дамп трафика, реплей, логи рассинхрона |

L0–L1 не знают про X-Ray и тестируются без игры. L2+ уже требует движка
и запуска игры.

## 6. Модель владения

- Хост владеет всем, кроме чужих игроков: NPC, предметы, аномалии, двери.
- Каждый клиент владеет только своим актором: его ввод, его позиция.
- Игроки идентифицируются `net_id = 1000 + слот` (у хоста — зарезервированный
  `1`), сущности мира — обычными игровыми ID. Соответствие `net_id ↔ game ID`
  хранит хост и рассылает вместе со спавном.

## 7. Репликация мира

1. Хост раз в тик собирает изменившиеся сущности (позиция, поворот, состояние)
   и складывает их в снапшот `coopnet` (interest management уже есть).
2. Клиент применяет снапшот к своим объектам. Для чужих игроков — интерполяция,
   для своего — реконсиляция предсказания.
3. Спавн: хост сериализует `CSE_Abstract` (`Spawn_Write`) и отправляет надёжным
   сообщением; клиент вызывает `CLevel::cl_Process_Spawn`, как при обычном
   спавне. Деспавн — отдельным сообщением по ID.
4. Статичные объекты (декор, аномальные зоны) не реплицируются: они есть
   в уровне у всех. Реплицируются только изменения.

Что и с какой частотой:

| Домен | Владелец | Частота | Точность |
|---|---|---|---|
| Позиция/поворот игрока | сервер (валидирует предсказание клиента) | 20 Гц снапшот, 60 Гц input | позиция ~6 мм, углы 16 бит |
| Состояние персонажа (стойка, оружие, анимация) | сервер | по изменению | enum + флаги |
| Выстрелы | клиент → сервер как намерение, сервер → всем как событие | событие | траектория/хит — сервер |
| Урон и здоровье | сервер | по изменению | u16 |
| NPC/мутанты | сервер | 10–20 Гц, по расстоянию | позиция + состояние AI |
| Предметы в мире | сервер | по изменению | id + трансформ |
| Инвентарь | сервер | по изменению | список слотов/стаков |
| Скриптовые события | сервер | событие | RPC по имени с аргументами |

Interest management: клиент получает сущности в радиусе и в «зоне сюжета»;
дальние NPC обновляются реже (LOD репликации). Реализовано: радиус 150 м,
keep-radius 165 м.

## 8. Акторы игроков

- Хост создаёт на каждого клиента актора-«болванку» (без HUD и управления)
  и привязывает к нему `net_id`.
- Клиенту при спавне приходит его собственный game ID: он становится
  `Level().CurrentControlEntity()`.
- Ввод клиента идёт по `C_INPUT` (ненадёжный канал, 60 Гц). Хост хранит
  последний ввод каждого пира и каждый кадр двигает куклу тем же контроллером,
  что и своего актора: `CPHMovementControl::Calculate` с ускорением из
  `g_cl_CheckControls`-правил и `CameraDir` из углов обзора. Физика и коллизии
  считаются только на хосте.
- Куклы, которых двигает хост, публикуются остальным как обычный `C_PLAYER`
  под `net_id` владельца (20 Гц). Свежий ввод владельца (0,5 с) отключает
  пересылку его собственного `C_PLAYER`, чтобы клиентское предсказание не
  спорило с авторитетом; без ввода трансформы снова идут напрямую.
- Чужие трансформы на клиенте не применяются рывками: мост держит два последних
  сэмпла игрока и отдаёт позу на 100 мс в прошлом (`PlayerInterpolator`,
  кратчайшая дуга по yaw). Задержка меньше интервала публикации не даёт
  интерполировать, больше — добавляет лаг; 100 мс — компромисс при 20 Гц.
- Клиент предсказывает своё движение в своём мире и пока не исправляется по
  снапшотам: реконсиляция появится вместе со снапшотами мира.

## 9. Время и тик

- Симуляция сервера — переменный `dt` кадра, как в оригинале, но сетевой тик
  фиксирован: 60 Гц приём/отправка ввода, 20 Гц снапшоты.
- Снапшоты нумеруются `tick` (u32) и строятся относительно подтверждённой базы
  (дельта).
- Клиент буферизует снапшоты на ~100 мс и интерполирует чужие сущности.
- Свой персонаж: предсказание, при расхождении — реконсиляция из последнего
  ack-снапшота.
- Физика X-Ray не детерминирована между машинами. Значит, физические объекты
  (ящики, трупы, тряпки) авторитетны на сервере, клиент их только интерполирует.
  Предсказывать можно исключительно кинематику персонажа по упрощённой модели.

## 10. Идентификаторы

- `object_id` в X-Ray — u16, уникален в пределах уровня и переиспользуется.
- `net_id`: u32, монотонный на сессию, выдаётся сервером при спавне сущности.
- Таблица `net_id → object_id` живёт на сервере и на клиентах; заполняется
  сообщением спавна.
- При смене уровня таблица очищается, `net_id` продолжают счёт (сквозная
  нумерация сессии).

## 11. ALife и скрипты

Сюжет Clear Sky — это скрипты (`task_manager`, `dialogs`, `xr_conditions`/
`xr_effects`, `smart_terrain`, `sim_squad_scripted`), а не движковые данные.
Поэтому кооп нельзя сделать «только на движке».

- **Story owner** — хост. Он единственный выполняет сюжетные скрипты в полном
  объёме и владеет состоянием задач. Симулятор ALife работает только у хоста;
  клиенту приходит уже результат: позиции, состояния, спавны.
- **Зеркало на клиентах.** Клиент не выполняет ветки логики, которые меняют мир;
  он получает состояние задач, активных диалогов и флагов и рисует UI.
  Скриптовые события в первой версии приходят клиенту как уведомления.
- **Диалоги.** Открывает один игрок; остальные видят, что диалог идёт, и не могут
  вклиниться. Выбор реплики — за инициатором.
- **Катсцены и рестрикторы.** Вход в катсцену блокирует ввод всем; камера —
  локальная, чтобы каждый видел сцену от себя.
- **Faction war.** Симуляция группировок целиком на сервере; клиент получает
  состояние точек и отношений. Действия любого игрока идут в общую симуляцию.

Практический приём: не переписывать скрипты CS, а обернуть их — перехватывать
`task_manager`, `dialogs` и `sim_squad_scripted` тонким слоем
`gamedata/scripts/coop/*`, который отправляет и применяет RPC. Это уменьшает
объём правок и упрощает откат.

## 12. Переходы между уровнями

Самый недооценённый кусок. В CS локации грузятся при переходе, вместе с ними
меняется весь мир и `object_id`. Сохранения и переходы делает хост; клиенты
ждут и переподключаются к новой локации, сверяя `C_WORLD`.

Двухфазный протокол:

1. Сервер фиксирует состав группы и запускает переход.
2. `S_LEVEL_PRELOAD` — клиенты грузят целевой уровень, показывают экран
   загрузки с прогрессом. Все шлют `C_LEVEL_READY`.
3. Когда все готовы (или истёк таймаут), сервер применяет переход: спавн группы
   на точке выхода, рассылка `S_LEVEL_GO` с новой таблицей сущностей.
4. Отвалившиеся в процессе — в лобби с возможностью реконнекта в тот же уровень.

Требуется остановка симуляции на время загрузки у всех: иначе игроки «живут»
в разных уровнях. Это осознанное ограничение: загрузка локации — общая пауза
5–15 секунд.

## 13. Сохранения и восстановление

- Сохранение делает сервер; клиентские сейвы не используются.
- Чекпойнт = состояние `alife()` + состояние уровня + позиции игроков +
  состояние задач.
- Реконнект клиента: полный снапшот мира (не дельта), возврат в ту же точку.
- Смерть игрока: `death`/`revive` — либо respawn у медика/базы, либо подъём
  напарником (решается на этапе M2, влияет на баланс).

## 14. Валидация и устойчивость

- Сервер проверяет скорость и телепорты игрока, попадания (по своим расчётам),
  дистанцию взаимодействия с предметами.
- Ограничение частоты и размера пакетов; неизвестные сообщения — лог и дроп,
  не краш.
- Версия протокола и хеш сборки проверяются на handshake: несовпадение —
  понятная ошибка, а не «невидимые игроки».

## 15. Бюджет производительности

Ориентир для 4 игроков и ~60 активных NPC:

- снапшот 20 Гц, дельта ≤ 1.5 КБ в среднем → ~240 Кбит/с на клиента;
- input 60 Гц, ~40 байт → ~20 Кбит/с;
- события/скрипты — по требованию, вне бюджета.

Если не влезаем — режем частоту для дальних сущностей, а не точность ближних.
Замеры — обязательная часть M1: без цифр оптимизировать нечего.

## 16. Порядок работ

1. **Спавн чужого игрока.** Хост спавнит второго актора, клиент получает его
   `CSE_Abstract` и видит второй силуэт. Код есть, проверяется только в игре.
2. **Ввод и предсказание в движке.** `C_INPUT` из `CActor` на клиенте,
   симуляция куклы на хосте, рассылка её трансформа. Код есть; предсказание и
   коррекция собственного персонажа — после снапшотов мира.
3. **Снапшоты мира.** Список сущностей из `Level().Objects`, interest
   по расстоянию, деспавн при выходе за радиус.
4. **Синхронизация оружия и урона.** Хост считает попадания, клиенты показывают
   эффекты.
5. **ALife-переходы.** Общая загрузка локации, пауза, переподключение.

## 17. Риски

| Риск | Почему опасен | Что делаем |
|---|---|---|
| Headless-сервер | X-Ray завязан на рендер и `Device` | спайк M1, при провале — listen-only |
| Несинхронная физика | физика не детерминирована | только серверная симуляция физики |
| Скрипты CS меняют мир напрямую | кооп ломает инварианты квестов | обёртки вместо переписывания, RPC-слой |
| Переходы уровней | общая пауза, потеря состояния | двухфазный протокол, тесты на каждой локации |
| Стоимость AI на сервере | 4 клиента + AI = CPU | LOD репликации, отключение дальнего AI |
| Объём работы | годы, а не месяцы | жёсткие этапы с критериями, вертикальный срез первым |

## 18. Проверка без игры

Всё, что выше уровня `coopnet`, компилируется, но не проверяется: нет легальной
копии Clear Sky 1.5.10. Автотесты покрывают транспорт, форматы сообщений,
предсказание и снапшоты; движковые хуки проверяются только сборкой и `dumpbin`.

## 19. Открытые вопросы

- Какой секцией спавнить «болванку» игрока в Clear Sky и какие флаги
  `M_SPAWN_OBJECT_*` нужны, чтобы не включился HUD и управление.
- Переживёт ли `CActor::net_Spawn` второго актора без `ASPLAYER` (там
  инициализируются реестры по ID).
- Что делать с квестовыми скриптами, которые ждут ровно одного актора.
- Как обходить сохранения, привязанные к одиночному игроку.
- Удастся ли обойтись listen-хостом или headless потребует развязки кадрового
  цикла от `CRenderDevice`.
